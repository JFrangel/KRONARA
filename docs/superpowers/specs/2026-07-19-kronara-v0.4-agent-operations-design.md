# Kronara v0.4 — Agente operativo, memoria y RAG verificable

Estado: diseño aprobado en conversación; especificación consolidada pendiente de revisión del usuario

Fecha: 2026-07-19

Ámbito: plano cognitivo, chat operativo, Reddit Observatory, herramientas visibles, memoria, RAG, embeddings y prueba narrativa

## 1. Resultado buscado

Kronara v0.4 convertirá el plano cognitivo actual en un asistente editorial operativo con personalidad propia, capacidad de investigación, memoria explícita y acceso gobernado a herramientas. El usuario podrá conversar con el sistema para entender qué está haciendo, por qué tomó una decisión, qué fuentes consultó, qué herramientas utilizó, cuánto costó y qué aprendió.

El objetivo no es fabricar una ilusión de inteligencia mediante un prompt monolítico. La capacidad provendrá de:

- contexto seleccionado y citado;
- agentes especializados;
- herramientas deterministas;
- modelos enrutados por capacidad;
- memoria versionada;
- recuperación híbrida evaluada;
- crítica independiente;
- trazas visibles;
- aprendizaje reversible con datos propios.

`full_auto` seguirá siendo el modo preferido, con límites no anulables. La autonomía nunca autoriza copiar contenido externo, entrenar con historias sin derechos, ocultar tool calls ni publicar cuando el estado remoto sea ambiguo.

## 2. Auditoría de la documentación v0.1

Se revisaron `DOMAIN_MODEL.md` y los catorce documentos incluidos en `KRONARA_DOCUMENTATION_v0.1.0.zip`. Sus decisiones útiles se conservan: dominio editorial independiente, artefactos versionados, contenido maestro, workflows reanudables, SQLite, Tauri/Rust, herramientas con mínimo privilegio, procedencia y publicación idempotente.

La v0.4 corrige estas divergencias:

1. El ADR-001 original decía que Python requería un ADR posterior. La arquitectura vigente ya adopta un sidecar Python aislado; debe registrarse un ADR que formalice a Rust como autoridad y Python como plano cognitivo.
2. La v0.1 asumía aprobación humana por defecto y excluía publicación autónoma del MVP. La política vigente usa `manual`, `supervised_auto` y `full_auto`, manteniendo bloqueos de derechos, seguridad, presupuesto y estado remoto.
3. La v0.1 describía Obsidian, un workspace Rust modular y varios estudios UI como objetivos, no como componentes terminados. La documentación no volverá a presentarlos como implementados.
4. El esquema conceptual de base de datos v0.1 es más amplio que las migraciones reales. Las tablas objetivo deben incorporarse por verticales y con pruebas de migración.
5. La v0.1 pedía tool observability, eventos de progreso, cancelación y un vertical audiovisual completo. Siguen siendo brechas verificables.

## 3. Personalidad del agente

La personalidad se define como configuración versionada, no como instrucciones dispersas:

- divertida sin convertir incidentes serios en bromas;
- independiente para cuestionar premisas y proponer alternativas;
- investigativa y curiosa ante vacíos de evidencia;
- perfeccionista respecto a contratos, continuidad y verificación;
- creativa al generar conceptos y soluciones;
- analítica al separar hechos, cálculos, inferencias e hipótesis;
- honesta sobre incertidumbre, disponibilidad de modelos y fallos de tools.

La personalidad nunca puede cambiar derechos, autoridad, evidencia ni outputs estructurados. El agente evita adulación automática, falsa seguridad, dramatización de métricas y afirmaciones de causalidad sin experimento.

## 4. Chat de operaciones

### 4.1 Alcance

`Operations Chat Agent` será la interfaz conversacional del sistema. Podrá responder:

- qué trabajos y agentes están activos;
- qué etapa está bloqueada y por qué;
- qué oportunidad o historia propia se está procesando;
- qué fuentes y evidencias sustentan una decisión;
- qué tool se utilizó y cuál fue su resultado resumido;
- qué modelo y alias se eligió;
- cuánto presupuesto se consumió;
- qué métricas cambiaron;
- qué aprendizajes están en hipótesis, prueba o promoción;
- cómo se recuperaría una ejecución interrumpida.

### 4.2 Autoridad

El chat es de lectura por defecto. Una petición que cambie estado produce un `ActionIntent@1`. Rust valida el intent contra modo de autonomía, riesgo, permisos, presupuesto e idempotencia. El LLM no llama directamente a publicación, filesystem, secretos ni procesos.

Acciones administrativas —políticas, derechos, presupuesto máximo, identidad editorial y fine-tuning— requieren confirmación explícita. La UI mostrará la propuesta y el resultado de la autoridad.

### 4.3 Contexto

El chat no recibe un volcado ilimitado de la base. `Context Engineer` compila un `OperationsContextPacket@1` con:

- snapshot del workflow;
- trabajos activos y últimos fallos;
- trazas de tools relevantes;
- evidencias y citas;
- métricas comparables;
- memoria conversacional resumida;
- reglas editoriales aplicables;
- presupuesto y estado de proveedores;
- artefactos exactos solicitados.

El paquete conserva hashes, versiones, vigencia, procedencia y nivel de confianza. La información recuperada se delimita como datos no confiables. Los secretos y el razonamiento privado no forman parte del contexto.

## 5. Prompt stack y skills

Los prompts se compondrán mediante capas versionadas:

```text
CorePolicy
→ PersonaProfile
→ AgentRole
→ TaskObjective
→ AuthorityAndBudget
→ ContextPacket
→ SelectedSkills
→ ToolContracts
→ OutputSchema
→ VerificationChecklist
```

Un prompt más largo solo se usa cuando añade contexto relevante. `Context Compiler` elimina duplicados, resume historial, preserva evidencia crítica y recupera información adicional cuando detecta vacíos.

Cada skill declara:

- `skill_id` y versión;
- capacidades;
- instrucciones y ejemplos aprobados;
- herramientas mínimas;
- contratos de entrada/salida;
- riesgos;
- evaluación normal, adversarial y golden;
- fecha de vigencia.

Skills nuevas: `operations_chat`, `context_engineering`, `tool_trace_explanation`, `reddit_observation`, `semantic_deduplication`, `retrieval_evaluation`, `embedding_evaluation` y `training_data_curation`.

## 6. Equipo objetivo de agentes

Se conservan los veinte agentes actuales y se añaden cuatro roles:

1. `operations_chat`: interpreta la operación y propone intents gobernados.
2. `context_engineer`: compila contexto relevante, citado y acotado.
3. `evaluation_scientist`: compara modelos, prompts, embeddings, rerankers y RAG contra baselines congelados.
4. `training_data_curator`: admite únicamente historias propias o licencias con scope verificable y construye dataset cards.

Todos los agentes tendrán manifiesto, herramientas permitidas, modelo/fallback, máximo de pasos, llamadas, costo, timeout, schemas y tests. El crítico debe usar, cuando sea posible, una familia distinta al generador.

## 7. ModelCapabilityRegistry v2

Los agentes solicitan aliases, nunca IDs externos. Configuración inicial:

| Alias | Uso | Candidatos |
|---|---|---|
| `fast_tools` | clasificación, JSON, tools y chat rápido | Groq resuelto desde catálogo vivo |
| `planning_primary` | planificación y estructuración | Qwen, fallback Nemotron/Kimi |
| `long_context_primary` | documentos y contexto largo | Kimi, fallback Nemotron |
| `deep_reasoning_primary` | deliberación y crítica adversarial | `nvidia/nemotron-3-super-120b-a12b:free`, fallback Kimi/Qwen |
| `experimental_hy3` | investigación larga experimental | `tencent/hy3:free`, fallback obligatorio |
| `creative_primary` | concepto y escritura | benchmark entre Qwen, Kimi, Nemotron y Hy3 disponible |

`tencent/hy3:free` anuncia retiro el 21 de julio de 2026 y nunca será el único candidato de una ruta. Los modelos gratuitos o preview tienen health check, circuit breaker y fecha de expiración. Groq consulta `/models` y respeta permisos de organización; no se fijan modelos deprecados como única ruta.

El router puntúa calidad medida, confiabilidad, latencia, costo, privacidad, contexto, structured output y tool calling. Guarda modelo solicitado, modelo resuelto, razón de selección, fallbacks y uso.

## 8. Herramientas y trazabilidad visible

### 8.1 Contrato

Toda invocación emite `ToolTraceEvent@1`:

```json
{
  "schema_version": 1,
  "event_id": "tte_...",
  "run_id": "run_...",
  "agent_id": "opportunity_intelligence",
  "tool_id": "reddit.list_signals",
  "status": "completed",
  "started_at": "...",
  "finished_at": "...",
  "duration_ms": 0,
  "arguments_redacted": {},
  "result_summary": "25 señales; 7 pasaron filtros",
  "evidence_refs": [],
  "artifact_refs": [],
  "cost_usd": 0,
  "retry": 0,
  "fallback": null,
  "policy_findings": []
}
```

No se persisten keys, tokens, bodies completos de historias externas ni razonamiento privado. Los argumentos se reducen a filtros y referencias seguras.

### 8.2 UI

La interfaz mostrará una línea de tiempo en vivo:

```text
Agente → Tool → Estado → Duración → Evidencia → Costo
```

El usuario podrá expandir una llamada para ver filtros, resumen, citations, reintentos y fallback. Fallos y bloqueos no se ocultarán detrás de un estado genérico.

## 9. Reddit Observatory

### 9.1 Límite contractual

Solo se utiliza OAuth y endpoints oficiales. Reddit permanece `disabled_by_policy` hasta que Rust confirme credenciales, `KRONARA_REDDIT_ENABLED=true` y una referencia contractual/administrativa. Los términos actuales restringen uso comercial no autorizado y entrenamiento con contenido de usuarios sin permiso expreso.

Fuentes normativas:

- <https://redditinc.com/policies/developer-terms>
- <https://redditinc.com/policies/data-api-terms>
- <https://www.reddit.com/dev/api/>

### 9.2 Autoridad y flujo

Rust carga secretos, valida host y política, ejecuta HTTP, rate limits, cache y paginación. Python solicita tools tipadas y recibe `TrendSignal`, nunca credenciales.

```text
reddit.status
→ reddit.list_signals
→ reddit.filter_signals
→ opportunity.score
→ rights.verify
```

### 9.3 Filtros

`RedditSignalQuery@1` soportará:

- uno o varios subreddits permitidos;
- `new`, `hot` o `top`;
- `hour`, `day`, `week`, `month`, `year` o `all` para `top`;
- paginación por cursor con máximo global;
- score y comentarios mínimos/máximos;
- edad mínima/máxima;
- idioma;
- self-post únicamente;
- incluir/excluir NSFW;
- palabras y temas incluidos/excluidos;
- longitud mínima/máxima observada sin persistir el cuerpo;
- autor/post eliminado;
- crosspost/repost;
- velocidad, aceleración, saturación y vida útil mínima;
- deduplicación por ID, URL y similitud de señal.

La tool devuelve títulos/permalinks cuando sea necesario para revisión, rasgos abstractos, engagement y metadatos de procedencia. El body solo vive durante la extracción autorizada y se descarta; no entra a RAG ni entrenamiento.

## 10. Memoria v2

Se mantienen memorias separadas:

1. ejecución: checkpoints y estado LangGraph;
2. episódica: decisiones y resultados por pieza;
3. semántica: reglas, ADN y aprendizajes promovidos;
4. rendimiento: voz, tema, hook, duración, horario y métricas;
5. conversación: resumen de preguntas, intents y decisiones del usuario;
6. errores: fallo, causa observada, corrección y evidencia de no regresión.

`Memory Curator` y `Training Data Curator` deciden qué puede persistirse. Cada memoria lleva ámbito, versión, procedencia, confianza, vigencia, derechos y evidencia. Las hipótesis rivales coexisten. Los mensajes del chat no se convierten automáticamente en política.

## 11. Historias propias exitosas

Una historia solo puede convertirse en ejemplo reusable si:

1. `rights_mode=owned_original` con procedencia de artefacto Kronara, o licencia que incluya entrenamiento;
2. pasó calidad narrativa, originalidad, seguridad y publicación;
3. acumuló una ventana comparable de métricas;
4. tiene muestra mínima y comparación contra cohortes de la misma plataforma/formato;
5. no depende de un único outlier;
6. no presenta señales de riesgo reputacional;
7. supera el golden set sin regresión al ser usada como ejemplo.

Estados:

```text
eligible_owned
→ measuring
→ supported_example
→ rag_candidate
→ promoted_rag_example
→ dataset_candidate
→ approved_training_example
```

`full_auto` puede promover ejemplos a RAG/few-shot dentro de límites reversibles. Fine-tuning requiere dataset card, splits congelados, volumen suficiente, benchmark contra RAG/prompt optimization y autorización administrativa.

## 12. RAG v3 y embeddings

### 12.1 Pipeline

```text
query classification
→ query decomposition
→ controlled expansion
→ rights/freshness/domain filters
→ FTS5/BM25
→ vector retrieval
→ typed GraphRAG
→ RRF
→ multilingual reranker
→ semantic deduplication
→ diversity
→ citation validation
→ context packet
```

SQLite conserva documentos, chunks, tombstones, embedding versions y aristas. FTS5 y sqlite-vec se conectan directamente al contrato v3; un cambio de embedding genera un índice nuevo y migración/rebuild, nunca mezcla dimensiones.

### 12.2 Embedding registry

`EmbeddingModelDescriptor@1` registra alias, proveedor, dimensiones, longitud, idioma, normalización, instrucciones de consulta, licencia, hash/versión, privacidad y health.

Candidatos iniciales:

- `BAAI/bge-m3`: multilingüe, 1024 dimensiones y documentos largos;
- `intfloat/multilingual-e5-large-instruct`: challenger multilingüe con instrucciones de query;
- fallback determinista actual: exclusivamente desarrollo, pruebas y recuperación degradada.

Reranker candidato: `BAAI/bge-reranker-v2-m3`. Ningún modelo se promueve solo por su model card. Debe superar el corpus narrativo español en Recall@k, MRR, nDCG, precisión de citas, redundancia, latencia y memoria.

Referencias:

- <https://huggingface.co/BAAI/bge-m3>
- <https://huggingface.co/BAAI/bge-reranker-v2-m3>
- <https://huggingface.co/intfloat/multilingual-e5-large-instruct>

## 13. Prueba de historia

La prueba actual aprobó 7 casos sobre concepto, blueprint, contexto citado, inyección y copia literal. No constituye una historia completa.

La prueba v0.4 usará un fixture `owned_original` y producirá:

```text
StoryBrief
→ 3 conceptos
→ selección explicada
→ blueprint causal
→ escenas
→ guion completo
→ continuidad
→ originalidad léxica/semántica/estructural
→ crítica independiente
→ revisión localizada
→ hook/retención
→ packaging
→ memoria propuesta
→ tool trace completo
```

Debe verificar duración, causalidad, semillas/revelaciones, personaje activo, payoff, originalidad, citas, derechos, herramientas usadas y ausencia de datos externos persistidos. Un caso adversarial introduce prompt injection y una historia fuente demasiado parecida; ambos deben bloquearse.

La prueba Reddit real es separada y opcional: consulta una lista pequeña mediante OAuth autorizado, conserva solo señales/metadatos y nunca se ejecuta como requisito de CI.

## 15. Persistencia

Se añaden migraciones para:

- conversations y conversation summaries;
- tool trace events;
- memory records y evidence links;
- embedding model versions e index manifests;
- Reddit query receipts sin bodies;
- owned story performance y reuse decisions;
- prompt stack manifests y skill versions.

Los artefactos grandes siguen direccionados por hash. Tool traces y chat nunca almacenan secretos. Tombstones y expiración se propagan a índices reconstruibles.

## 16. Fallos y degradación

- Reddit sin autorización: `disabled_by_policy`, sin datos simulados en producción.
- Rate limit: receipt visible, retry programado y cache segura.
- Modelo gratuito retirado: circuit breaker y fallback.
- Embedding no disponible: último índice compatible o búsqueda léxica degradada; no mezclar vectores.
- Reranker caído: RRF con warning visible.
- Tool fallida: evento `failed`, causa segura y acción de recuperación.
- Contexto insuficiente: respuesta parcial con vacíos explícitos.
- Métricas insuficientes: historia permanece `measuring`.
- Acción sensible desde chat: `requires_approval`.

## 17. Seguridad

Rust mantiene secretos y efectos externos. Las tools son default-deny. Reddit, RAG y chat tienen límites de payload, llamadas, costo y tiempo. El contexto externo se trata como datos; la inyección no puede ampliar permisos. La UI muestra argumentos redactados.

Antes de publicar el repositorio se ejecutan secret scan, comprobación de `.env` ignorado, pruebas, build y revisión de remoto. La publicación a GitHub requiere confirmar propiedad y visibilidad del destino.

## 18. Fases de implementación

1. ADR Python sidecar, contratos v0.4 y migraciones.
2. Tool trace persistente y timeline visible.
3. Operations Chat, personalidad, prompt stack y contexto.
4. Model registry v2 con Groq, Nemotron, Hy3, Qwen y Kimi.
5. Reddit tools gobernadas desde Rust, filtros y receipts.
6. Memoria v2 y promoción de historias propias exitosas.
7. RAG v3 persistente, embedding registry y reranker.
8. Golden español ampliado y prueba de historia completa.
9. UI no técnica de operación, tools, evidencia y chat.
10. Gate integral, integración en `main` y publicación.

## 19. Criterios de salida

- El chat responde sobre la operación usando contexto verificable y citas.
- Toda tool aparece en la timeline con argumentos redactados y resultado.
- Reddit real solo funciona con OAuth y aprobación; sus bodies no se persisten.
- El agente usa al menos una tool cuando la pregunta lo requiere y no finge usarla.
- Los cuatro agentes nuevos tienen contratos, límites, skills y tests.
- RAG v3 supera el baseline congelado con un embedding real o mantiene el candidato sin promover.
- Una historia propia exitosa puede promoverse a RAG y revertirse.
- Una historia externa no puede entrar en RAG creativo ni dataset.
- La prueba narrativa completa genera artefactos, crítica, revisión y trazas recuperables.
- Reinicio, rate limit, modelo retirado, tool failure y prompt injection se recuperan o bloquean correctamente.
- El repositorio se publica solo después de que todas las suites y builds pasen.

## 20. Fuera de alcance inmediato

- Entrenar un foundation model desde cero.
- Guardar razonamiento privado paso a paso.
- Usar scraping de Reddit.
- Fine-tuning automático sin aprobación.
- Permitir al chat ejecutar shell o leer secretos.
- Afirmar que una historia será viral.
